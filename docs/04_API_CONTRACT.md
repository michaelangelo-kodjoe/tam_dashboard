## 0. Conventions

- Base: `http://127.0.0.1:<port>` (PROD 8765, DEV 8766, `TAM_PORT` overrides). Loopback only. Requests whose `Host` is not `127.0.0.1` or `localhost` are refused (DNS-rebinding guard). Non-GET requests with an `Origin` header must be same-origin, or (DEV only) the Vite origin `http://127.0.0.1:5173` / `http://localhost:5173`; otherwise 403 `forbidden_origin`. CORS is enabled only for those DEV origins.
- All bodies are JSON (`Content-Type: application/json`). All responses are JSON and carry `Cache-Control: no-store`.
- **Unknown request fields are rejected** (422). Strings are trimmed; an empty string on an optional field means `null`.
- **Dates** are `YYYY-MM-DD` (no timezone, local calendar date, D-06). **Instants** are UTC `YYYY-MM-DDTHH:MM:SS.sssZ`. Input instants may carry an offset or omit milliseconds; they are normalised to UTC. An input with no offset is treated as UTC.
- **Booleans** are JSON booleans (`is_primary`, `archived`, `enabled`).
- Every row payload includes `row_version` (integer). Send it back as `expected_row_version` on updates (D-11).
- "Today" (`today`) is the workstation's local date, computed by the server.

### 0.1 Envelopes

Success: `{"ok": true, ...}`. Mutations return `{"ok": true, "item": {...}, "side_effects": [...]}` (`side_effects` is always present, possibly `[]`).

Side effects are objects with a `type`:

| type | extra fields | meaning |
|---|---|---|
| `primary_cleared` | `contact_id`, `name` | contact `contact_id` was primary and has been cleared by this save (toast: "B is now primary (was A)") |
| `next_contact_updated` | `client_id`, `old`, `new` | D-07: the account's `next_contact` was moved |
| `last_contact_updated` | `client_id`, `old`, `new` | D-08: the account's `last_contact` was moved |
| `backup_created` | `file`, `reason` | a safety backup was written before a delete |
| `no_change` | | the save changed nothing; `row_version` was not bumped and nothing was audited |

Error:
```json
{"ok": false, "error": {"code": "validation_error", "message": "Request validation failed.",
                        "fields": {"due": "must be a date in YYYY-MM-DD format"},
                        "details": {}}}
```
`fields` appears on `validation_error` and field-level `conflict`; `details` is an optional free-form object (additive).

| code | HTTP | when |
|---|---|---|
| `validation_error` | 422 | schema/enum/date/length/unknown-field errors, unknown referenced account |
| `not_found` | 404 | unknown id or unknown `/api/...` path |
| `confirmation_required` | 409 | `*/delete` without `confirm: true` (or account delete without matching `confirm_name`) |
| `stale_write` | 409 | `expected_row_version` does not match. `details.current_row_version` is given |
| `conflict` | 409 | uniqueness: duplicate account name (case-insensitive), second primary contact, ... |
| `payload_too_large` | 413 | request body over 2 MB (`details.max_bytes`); checked before the body is parsed (additive, Phase 4.1) |
| `not_implemented` | 501 | later-phase route |
| `method_not_allowed` | 405 | wrong method on a known path, with an `Allow` header and `details.allowed` (additive; before Phase 4.1 `/api/...` paths answered 404) |
| `forbidden_origin` | 403 | cross-origin write / bad Host (additive) |
| `backup_failed` | 500 | the safety backup could not be written; the delete did **not** happen |
| `internal` | 500 | unexpected error (details are in the server log, not in the response) |

### 0.1a Response headers and limits (Phase 4.1, additive)
Every response, including errors and the SPA, carries `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`. The compiled bundle loads with no violations. Request bodies larger than 2 MiB (`MAX_BODY_BYTES`, declared or chunked) get 413 `payload_too_large`. The largest legitimate body (a 50000-character note) is far below the cap.

### 0.2 Update semantics

`POST /api/<object>/save` is an upsert: **no `id` creates, `id` updates**. Updates are **patches**: only the fields present in the body change; send `null` to clear an optional field. Required fields on create are listed per route. `id` is generated by the server (UUID4) and cannot be supplied on create.

If `expected_row_version` is sent and differs from the stored `row_version` -> 409 `stale_write`. If it is omitted, the write is unconditional. Updating a missing id -> 404 `not_found`.

## 4. Writes

All writes are one SQLite transaction containing the data change **and** its `audit_events` row(s). All return `{"ok": true, "item": ..., "side_effects": [...]}` with the saved row. HTTP 200 for create and update.

### `POST /api/client/save`
| field | type | notes |
|---|---|---|
| `id` | string | omit to create |
| `expected_row_version` | int | update only |
| `name` | string 1..200 | required on create; unique case-insensitive -> 409 `conflict`; no tab/CR/LF |
| `bpid` | string ≤32 \| null | |
| `products` | string ≤500 \| null | |
| `status` | `Active` \| `Inactive` | default `Active` |
| `next_contact` | date \| null | |
| `notes` | string ≤20000 \| null | |

Returns an **Account** (with `counts`). Audit: `client.created`; on update one `client.next_contact_changed` and/or `client.status_changed` row for those fields, plus one `client.updated` row for the remaining changed fields.

### `POST /api/client/delete`
`{"id", "confirm": true, "confirm_name": "<exact account name>", "expected_row_version"?}`. Missing `confirm` or a `confirm_name` that does not equal the stored name (exact, trimmed) -> 409 `confirmation_required`. A `pre-delete` safety backup is taken first; if that fails -> 500 `backup_failed` and nothing is deleted. Cascades to contacts, notes, tasks, upgrades and BAMS objects (D-12). Audit `client.deleted` (history survives). Returns `{"ok": true, "item": {"id": "…", "name": "…"}, "side_effects": [{"type": "backup_created", ...}]}`.

### `POST /api/contact/save`
Fields: `id`, `expected_row_version`, `client_id` (required on create; immutable afterwards), `name` (1..200), `role` (≤200), `email` (≤254, optional, must look like `x@y.z`), `team` (≤200), `is_primary` (bool, default false).

Primary rule: setting `is_primary: true` clears any other primary of the same account **in the same transaction**; side effect `primary_cleared`. An account may have zero primaries. Audit: `contact.created` / `contact.updated` for field changes, plus `contact.primary_changed` (`old_value.primary_contact`, `new_value.primary_contact`) when the primary designation changes. "Make primary" is `{"id", "is_primary": true}`.

### `POST /api/contact/delete`
`{"id", "confirm": true, "expected_row_version"?}`; safety backup first; audit `contact.deleted`.

### `POST /api/task/save`
Fields: `id`, `expected_row_version`, `task` (1..500, no tab/CR/LF, required on create), `client_id` (nullable), `category` (default `Other`), `priority` (default `Medium`), `status` (default `Not Started`), `due`, `next_update`, `waiting` (≤500), `notes` (≤20000), `update_next_contact` (bool, default **false**; see D-07).

- D-07: when `update_next_contact` is true, `category` is `Client Follow-Up`, `client_id` and `due` are set, and the account's `next_contact` is empty or later than `due`, the account's `next_contact` is set to `due` in the same transaction (own audit row, `source=System`); side effect `next_contact_updated`. Quick Capture "Client Follow-Up" sends `true` by default (the checkbox).
- Audit: `task.created`; `task.completed` when status becomes `Complete`; `task.reopened` when it leaves `Complete`; otherwise `task.updated`.
- Mark complete: `{"id", "expected_row_version", "status": "Complete"}`.

### `POST /api/task/archive`
`{"id", "archived": true|false, "expected_row_version"?}` -> audit `task.archived` / `task.unarchived`.

### `POST /api/task/delete`
`{"id", "confirm": true, "expected_row_version"?}`; safety backup first; audit `task.deleted`.

### `POST /api/note/save`
Fields: `id`, `expected_row_version`, `client_id` (required on create; immutable), `note_type` (required on create), `timestamp` (instant; default now), `subject` (≤200), `body` (≤50000), `action_items` (≤10000). At least one of `subject`/`body` must be non-empty. `source` is not accepted (server sets `GUI`).
D-08: saving a `Meeting Note` or `Call Note` whose local date is later than `last_contact` sets `last_contact` (audit `client.last_contact_changed`, `source=System`); side effect `last_contact_updated`. General Notes never do.
Audit: `note.created` / `note.updated`.

### `POST /api/note/delete`
`{"id", "confirm": true, "expected_row_version"?}`; safety backup first; audit `note.deleted` (shows in Activity as "Meeting Note deleted: <subject>").

## 9. Run 2 additions (additive; T-62 to T-64, PM-AC-1..3, D-27 D-29 D-31 D-33)

No frozen field, route or error code changes. No schema change. All three are read-only GETs, loopback-only, `Cache-Control: no-store`, with the usual security headers.

### 9.1 `progress` on `GET /api/today` (PM-AC-1, D-29)
```json
"progress": {"day": "2026-10-13", "total": 8, "done": 3, "open": 5, "done_other": 1}
```
All five keys are always present; the four counts are integers >= 0. `day` echoes `today`. `total = done + open`, so `done <= total` always. `queue`, `upcoming`, `recent_changes` and `account_load` are unchanged (same items, same order).

Rules (PM §10.2, executed by the reference query `db/queries/day_progress.sql` unmodified): tasks only. Plan task = `due IS NOT NULL AND due <= today`, account Active or none, and either open (status not Complete, not archived) or done today. `done` = plan tasks with status Complete now and a `task`/`completed` audit row inside the local-day window (counted once per task; archived is ignored for done tasks). `open` = open plan tasks. `done_other` = completed today under the same rules but `due > today` or `due` NULL. Tasks on Inactive accounts are excluded from all four. Deleted tasks are not counted.

Day window: the server converts the local midnight of `today` and the local midnight of `today + 1 day` to UTC **separately** (`[start, end)`), so a 23-hour or 25-hour DST day is exact. The timezone is the workstation zone (the same clock as `today`).

### 9.2 `GET /api/accounts/activity-trend?days=14` (PM-AC-2, D-31)
Query: `days` (optional, default and only accepted value **14**; any other value -> 422 `validation_error`; the query is fixed at 14 buckets), `include_inactive` (optional boolean `true|false`, default `false`).
```json
{"ok": true, "today": "2026-10-13", "days": 14,
```

### 9.3 `server_tiles` on `GET /api/client/{id}/infrastructure` (PM-AC-3, D-31)

```json

  {"name": "bxa-ny-01", "environment": "PROD", "version": "7.1.4", "alert_severity": "Critical",
   "spark": {"metric": "Disk", "window_hours": 168, "points": [["2026-10-06T12:00:00.000Z", 71.2], ["2026-10-06T18:00:00.000Z", 73.0]]}},
  {"name": "bxa-ldn-02", "environment": "DEV", "version": null, "alert_severity": null, "spark": null}

```
One tile per **distinct server name** (case-insensitive across `bams_objects.name` and `server_upgrades.server_name`), ordered by name (case-insensitive, then exact). The first-seen spelling is used (BAMS object name preferred).

| field | rule |
|---|---|
| `name` | server name |
| `environment` | `PROD` / `DEV` / `null`; same precedence as the `environment_summary` (upgrade rows, most recent release first, else the BAMS object) |
| `version` | `current_version` of the server's earliest open upgrade (status not Completed/Deferred, by `scheduled_date`, nulls last), else `target_version` of its latest Completed upgrade, else `null` |
| `alert_severity` | `Critical` / `Warning` / `Info` = worst **open** alert on the server's enabled BAMS metrics, else `null` (healthy) |
| `spark` | object or `null` |

`spark` metric choice (one metric per server): (1) the metric of the server's highest-severity open alert (ties: earliest `opened_at`, then id); else (2) an enabled metric whose name contains `cpu` (case-insensitive; ties by name, then id); else none. `spark` is `null` when there is no such metric, the server exists only as upgrade records, or the chosen metric has no samples in the window. Never invented.

Window: samples with `sampled_at` in the last 7 days (queried by `metric_id` and a `sampled_at` range only; older rows are never read, §45). `window_hours` = whole hours from the first sample in the window to now, rounded up, capped at 168 (so "CPU 24h" for a day of data, "Disk 7d" at 168). `points` = `[iso_utc, value]` pairs, oldest first, **at most 28**: if the window holds more than 28 samples, the span from the first to the last sample is split into 28 equal-time buckets and each non-empty bucket contributes its maximum value at that sample's timestamp. PROD has no `spark` until the Phase 4 monitor writes samples.


### 10.4 `POST /api/import/accounts/apply`
```json

   {"row": 4,  "choice": "same",      "target": {"type": "account", "id": "…"}},
```

Unknown fields are rejected (422). Order of checks: `confirm` must be `true` (else 409 `confirmation_required`); session (410 `import_expired`; 409 `already_applied`); another Apply running (409 `conflict`); the plan is **re-run against the current database** and its `plan_hash` compared (409 `preview_stale`); `decisions` validated against the fresh plan (422 `validation_error` for a duplicate entry, a row that is not `needs_review`, `same` without `target`, a `target` on `different`/`skip`, a `target` that is not one of that row's candidates, or `same` onto a row that is skipped); a `needs_review` row without a decision -> 409 `unresolved_duplicates` (`details.rows`). Any exception rolls the whole transaction back. If the plan changes nothing: no backup, no transaction, no audit, `backup: null`.

Merge rules (D-43): fill blanks only (`bpid`, `products`, `next_contact`, `notes`); a non-blank value is never changed, appended to or replaced; an Inactive account stays Inactive; earlier rows win over later rows; a new account's blank Status becomes `Active`.

### 11.0 Vocabulary

- `freshness`: `"Live" | "Delayed" | "Stale" | "No Data"` (same spelling as `worst_status` in §3). Rule (D-52, amended 2026-10-16): age = server now minus `last_received` (the last SUCCESSFUL valid receipt; not the value-change time); Live when age <= `live_seconds`, Delayed when <= `stale_seconds`, else Stale; `No Data` when no value exists, **always** when the provider is unavailable (PROD fail-closed). `live_seconds = max(poll_interval_seconds + 15, 75)`; `stale_seconds` = the metric's `stale_after_seconds` (default 120). - `alert_status`: `"open" | "recovered" | "closed"`. "Active" = `open` or `recovered` (D-59).
- `severity`: `"Info" | "Warning" | "Critical"`. `rule_type`: `"fixed_threshold" | "pct_of_high" | "exceeds_high"` (schema names, see §11.12 item 1). `operator`: `">" | ">=" | "<" | "<="`. `reference_period`: `"30d" | "60d" | "90d"`.
- `display_status` (the worst of alert state and freshness, D-58; precedence): `"open" > "recovered" > "stale" > "no_data" > "delayed" > "live"`, or `"disabled"`.
- Numbers are JSON numbers (never formatted strings). `null` means unknown. Highs carry a date only (`YYYY-MM-DD`), not a time (schema).
- Every instant is UTC (§0). Ages are integer seconds computed by the server (`age_seconds`), so the client never needs a clock match.

`desired_running` is the persisted Start/Stop choice (DEV default true; PROD default false until Start). `state` is the real state: `provider_unavailable` whenever the provider cannot deliver (PROD stub always; DEV during a simulated outage), regardless of `desired_running`. `last_error` is a short sanitized sentence or `null`. `next_poll_at` is `null` unless `state` is `running`.

**Provider** (`provider`): `{"mode": "DEV|PROD", "kind": "simulated|blpapi", "available": true, "simulated": true, "message": null}`. `simulated` is true only in DEV with the simulator (UI shows the SIMULATED badge). No route can change `mode`, `kind` or `simulated`.

**Row** (one metric; used by state, detail, and alerts context):
```json

 "stale_after_seconds": 120, "row_version": 3,
 "object": {"id": "…", "name": "BPOD-NY-01", "client_id": "…", "client_name": "Castellan Peak Global Markets",

 "alert": {"id": "<event_id>", "status": "open", "severity": "Warning", "opened_at": "…Z"},

```
`current_value` is `null` (and `freshness "No Data"`) when there is no value or the provider is unavailable; a number is **never** shown without a provider. `alert` is the most severe active event (ties: oldest open first) or `null`; `active_alerts` counts all active events on the metric. `spark` (<= 24 points, last 24 h, oldest first) appears on `state` rows only and is `[]` when empty; `?spark=0` omits it. `simulated` is true when the value comes from the simulator.

**Rule**: `{"id","metric_id","rule_type","operator","threshold","reference_period","consecutive_updates","severity","cooldown_minutes","enabled","suppress_until_clear","breach_count","preview","row_version","created_at","updated_at"}`. `preview` is the backend sentence (display it): fixed `Alerts when CPU utilisation % > 85 for 3 updates (Warning)`; pct_of_high `Alerts when Active sessions > 90% of the 90-day high (1,755) for 2 updates (Critical)`; exceeds_high `Alerts when Active sessions exceeds the 90-day high (1,755) for 1 update (Critical)` (the number is omitted when the high is unknown). `suppress_until_clear` is the DA's runtime flag (docs/03_DATA_MODEL.md section 18): the lifecycle sets it when the user Closes a still-breaching alert and clears it when the metric clears; while true a breach does not open an event (D-53). It is also writable (mockup 05 toggle): `true` suppresses until the next clear, `false` lifts it.

**Alert event**:
```json
{"id": "…", "metric_id": "…", "rule_id": "…|null", "alert_type": "fixed_threshold", "severity": "Warning",

```
`still_breaching` (active events only; `false` once closed) is true when the metric is fresh and the rule currently breaches: the Close dialog shows its warning from this. `rule_summary` is the short condition kept even if the rule was later deleted (`rule_id` null).

### 11.2 `GET /api/bams/state`

Cached state only: **never triggers a provider call** (D-51); safe to poll every 15 s. Query (all optional, combine with AND):

| param | values |
|---|---|
| `view` | `all` (default), `active_alerts`, `delayed_stale`, `live`, `no_data` |
| `account` | client id, or comma-separated ids (the import's "Open BAMS" passes several) |
| `object_id`, `location` (exact, NOCASE), `metric` (metric name, exact NOCASE) | |
| `status` | `open`, `recovered`, `live`, `delayed`, `stale`, `no_data` (matches `display_status` components: `open`/`recovered` match `alert.status`, the others `freshness`) |
| `q` | substring, NOCASE, over appliance, account, metric name and ticker (<= 100 chars) |
| `sort` / `dir` | `status` (default, worst first, then appliance, then metric), `appliance`, `location`, `metric`, `current`, `high30`, `high60`, `high90`, `last_update`; `asc` (default) / `desc`. `null` values sort last |
| `include_disabled` | `false` (default). Disabled appliances and metrics are otherwise omitted and not counted |
| `spark` | `1` (default) / `0` |

Unknown param values -> 422 `validation_error`. Response:
```json
{"ok": true, "server_time": "…Z", "monitor": {…}, "provider": {…},
 "banner": null,
 "summary": {"active_alerts": 2, "open": 1, "recovered": 1, "delayed": 2, "stale": 1, "delayed_stale": 3, "live": 5, "no_data": 1, "total": 10},

```
- `summary` covers all enabled metrics (strip on the page; active_alerts = events, the others = metrics). `view_counts` are the tab counts and respect every filter **except** `view`. `filters` lists the choices from the whole enabled set (not narrowed). `counts.rows` = rows returned (after all filters); there is no pagination (hard cap 2000 rows; over it `counts.truncated: true`).
- `banner` is `null` or `{"code": "provider_unavailable", "text": "BLPAPI provider is not connected. No live values are shown."}` (PROD stub, or a DEV simulated outage with the text `Simulated outage (DEV)`). With a banner every row has `freshness "No Data"`, `current_value null`.

### 11.3 Metric detail and trend

`GET /api/bams/metric/{id}` -> `{"ok": true, "item": {"row": <Row>, "rules": [<Rule>], "alerts": [<Alert event>], "alerts_total": 14, "ranges": ["24h","7d","30d","90d"]}}`. `alerts` = this metric's history, newest first, <= 50 (`?alerts_limit=` 1..200). Works for disabled metrics. 404 `not_found` otherwise.

`GET /api/bams/metric/{id}/trend?range=24h|7d|30d|90d` (default `7d`):
```json
{"ok": true, "item": {"metric_id": "…", "range": "7d", "from": "…Z", "to": "…Z",
  "points": [{"t": "…Z", "v": 88.1}], "downsampled": true,
  "text": {"min": 62.0, "max": 93.4, "last": 91.4, "count": 420, "from": "…Z", "to": "…Z"},
  "reference_lines": [{"id": "high_30", "label": "30D high", "value": 94.1, "date": "2026-10-03"}, {"id": "high_60", …}, {"id": "high_90", …}],
  "rule_lines": [{"rule_id": "…", "label": "Warning threshold 85", "value": 85, "severity": "Warning"}]}}
```
`points` <= 500 (time buckets, mean of the bucket, oldest first; `text.min/max/last/count` are computed from the **raw** samples so the text equivalent is exact). `rule_lines` gives one line per enabled rule whose level is a number (fixed: threshold; pct_of_high: threshold% of the period high; exceeds_high: the period high). Empty history or provider unavailable -> `points: []`, `text` values `null`, `count 0` (200, not an error). Bad `range` -> 422.

### 11.4 Alerts

`GET /api/bams/alerts?status=active|open|recovered|closed|all` (default `active`; `account`, `metric_id`, `limit` 1..500 default 100, `before` = an `opened_at` instant for paging):
```json
{"ok": true, "counts": {"active": 2, "open": 1, "recovered": 1, "closed": 14},
 "items": [{"event": <Alert event>, "metric": {"id","metric_name","ticker"}, "object": {"id","name","client_id","client_name","location"}, "freshness": "Live"}],
 "next_before": null}
```
Order: active first (open, then recovered; most severe, then oldest), then closed newest first. `status=closed` is the "Closed history" view. Counts ignore `limit`. Alerts on disabled objects/metrics are not listed in `active` (as §3); `closed` lists them.

`POST /api/bams/alert/{id}/close` body `{"note": "…"|null, "expected_row_version": 4}` (`note` <= 2000; strict). Allowed from `open` or `recovered`. Success `{"ok": true, "item": {"event": <Alert event, status closed>, "suppressed_until_clear": true}, "side_effects": [...]}`; `suppressed_until_clear` is true when the metric was still breaching (D-53): the rule is suppressed until the value clears, then a fresh breach opens a new event. Writes an audit event (`source UI`, category `bams`, reason = note) and the activity sentence `BAMS alert closed: <subject> (<severity>)` (§7). Errors: 404; 409 `stale_write`; 409 `conflict` with `details.reason "already_closed"`. A frozen monitor (stale or outage) does not block Close.

### 11.5 Monitor and settings

`POST /api/bams/monitor/start` and `/stop`: body `{}` (strict). Return `{"ok": true, "item": {"monitor": <Monitor>}}` and persist `desired_running`. Idempotent (starting a running monitor is a 200 no-op, no audit). In PROD with the stub provider, start answers 200 and `monitor.state "provider_unavailable"` (it never simulates). Start/stop write an audit event (category `bams`, `source UI`). `GET /api/bams/monitor` **(+)** returns `{"ok": true, "monitor": …, "provider": …}` cheaply for the header strip.

`GET /api/bams/settings` -> `{"ok": true, "item": <Settings>}`; `POST /api/bams/settings` takes a partial body (only present keys change) and returns the full `item`:
```json
{"poll_interval_seconds": 60, "in_app_notifications": true, "desktop_notifications": true,
 "notify_recovered": false, "privacy_mode": true}
```
`poll_interval_seconds`: integer 30..86400 (presets 60/120/300/600 are a UI matter). `notify_recovered` applies to **desktop** only; the in-app inbox always records recovered. Defaults per the 2026-10-14 answers: desktop on, privacy on, monitor stopped in PROD. Persisted in `app_meta` as `setting.bams.*`; changes are audited (old/new value). Changing `poll_interval_seconds` takes effect at the next cycle. The UI refresh interval (15 s) is a frontend preference and is not stored by the server.

### 11.6 Appliances (objects) and metrics

`POST /api/bams/object/save` (upsert, §0.2):
```json
{"id": "…|omit", "client_id": "…", "name": "BPOD-NY-01", "region": "Americas", "location": "New York",
 "environment": "PROD|DEV|null", "enabled": true, "expected_row_version": 2,
 "metrics": [{"id": "…|omit", "metric_name": "CPU utilisation %", "ticker": "BPOD1 CPU", "enabled": true,
              "stale_after_seconds": 120, "expected_row_version": 1}]}
```
- Create requires `client_id` (existing account, else 422), `name`, and `metrics` with **at least one** metric (`metric_name`, `ticker` required). `client_id` cannot change on update.
- Update patches the object fields. `metrics`, if sent, is an **upsert-only** list (item with `id` patches, without `id` creates); it never removes a metric (use metric/delete). Object and metrics are written in one transaction; any failure writes nothing.
- Limits are the schema limits: name 1..200 (trimmed, spaces collapsed, no control characters), region <= 100, location <= 200, ticker 1..200, `stale_after_seconds` integer >= 1.
- Errors: 409 `conflict` `fields.name` "An appliance named X already exists for this account." (NOCASE, per account); 409 `conflict` `fields["metrics[1].ticker"]` "Ticker T is already used by <metric> on <appliance>." with `details.owner = {metric_id, metric_name, object_name, client_name}` (tickers are globally unique; also raised for a ticker repeated inside the same request, `fields` naming both indexes); 409 `conflict` for a repeated metric name inside one appliance; 422 field errors; 404/409 `stale_write` as usual.
- Response `{"ok": true, "item": {"object": {…, "metrics": [{id, metric_name, ticker, enabled, stale_after_seconds, row_version}]}}, "side_effects": []}`; `no_change` when nothing changed. Disabling an appliance does not touch its alerts; disabled items drop out of counts and `state` (their active events stay stored, hidden from active lists until re-enabled, §3).
- A new metric shows **No Data** until the next poll; the monitor reads the metric list at the start of every poll, so no restart is needed. In DEV the simulator invents values for any new ticker deterministically.

`POST /api/bams/metric/save` (upsert): `{"id","object_id" (create),"metric_name","ticker","enabled","stale_after_seconds","expected_row_version"}`. Same limits and conflicts. `ticker` of an existing metric may be changed here (not by import); changing it clears `current_value`, `last_source_update`, highs and samples are kept (history belongs to the metric), and the next poll refills.

`GET /api/bams/object/{id}/delete-preview` **(+)** and `GET /api/bams/metric/{id}/delete-preview` **(+)** -> `{"ok": true, "item": {"name": "BPOD-NY-01", "metrics": 2, "samples": 25120, "rules": 3, "alerts_total": 5, "alerts_active": 1, "blocked": true, "blocked_reason": "1 alert is still open or recovered. Close it first."}}` (mockup 06b states these counts).
`POST /api/bams/object/delete` / `/metric/delete`: `{"id": "…", "confirm": true, "expected_row_version": n}`. Without `confirm: true` -> 409 `confirmation_required` with `details` = the preview item. **Blocked while any non-closed alert exists** on the object or metric: 409 `conflict`, `details.reason "active_alert"` (nothing written, no backup). Otherwise a `pre-delete` safety backup, then delete (metrics, rules, samples, closed events, notification rows go by cascade). Response `{"ok": true, "item": {"deleted": {"id", "name", "metrics", "samples", "rules", "alerts"}}, "side_effects": [backup_created]}`; `backup_failed` 500 aborts the delete. Audit event per delete (category `bams`).

### 11.7 Rules

`POST /api/bams/rule/save` (upsert): `{"id", "metric_id" (create), "rule_type", "operator", "threshold", "reference_period", "consecutive_updates", "severity", "cooldown_minutes", "enabled", "suppress_until_clear", "expected_row_version"}`. Defaults on create: `operator ">"`, `consecutive_updates 1`, `severity "Warning"`, `cooldown_minutes 0`, `enabled true`, `suppress_until_clear false`. Validation runs on the merged result and returns field messages matching the schema CHECKs:
- `fixed_threshold`: `threshold` required (any number), `reference_period` must be null.
- `pct_of_high`: `threshold` required and > 0 (a percent of the high, 90 = 90%), `reference_period` required.
- `exceeds_high`: `reference_period` required, `threshold` must be null, `operator` must be `>` or `>=`.
- `consecutive_updates` >= 1 (<= 1000), `cooldown_minutes` 0..10080. Changing `rule_type` on update re-validates everything; unrelated fields are cleared only if sent as `null`.
Messages, e.g. `fields.threshold "Threshold is required for a threshold rule."`, `fields.consecutive_updates "Consecutive updates must be 1 or more."`. Response `{"ok": true, "item": {"rule": <Rule>}, "side_effects": []}`. Editing a rule resets its `breach_count`; `suppress_until_clear` changes only if sent. A rule change never opens or closes an event by itself; the next fresh poll evaluates it.

`POST /api/bams/rule/delete`: `{"id", "confirm": true, "expected_row_version"}`; no confirm -> 409 `confirmation_required`. Allowed with an active event: the event stays (its `rule_id` becomes null, `rule_summary` is kept), is no longer evaluated, and ends only by a user Close. No backup (small row). Audit (category `bams`) for save and delete, `source UI`.

### 11.8 Starter templates (alert configs)

`GET /api/bams/configs` -> `{"ok": true, "items": [{"id","name","metric_match":"*CPU*","rule_type","operator","threshold","reference_period","consecutive_updates","severity","cooldown_minutes","enabled","starter","row_version","preview":"Alerts when a matching metric > 85 for 3 updates (Warning)","matches": 4}]}`. `metric_match` is a GLOB pattern tested case-insensitively on `metric_name`; `matches` counts enabled metrics on enabled appliances. Seeded starters per the default of question 3: one `exceeds_high` 90d Warning and one `pct_of_high` 90%/90d Critical (user editable).

**(+)** `POST /api/bams/configs/save` (upsert, same validation and fields as a rule plus `name` 1..200 unique NOCASE and `metric_match` 1..200, no control characters) and `POST /api/bams/configs/delete` (`id`, `confirm: true`). Templates are not rules; no event depends on them. Audited.

`POST /api/bams/configs/apply`: `{"config_id": "…", "metric_ids": ["…"]|null, "preview": true, "confirm": false}`.
- `preview: true` (default) writes nothing: `{"ok": true, "item": {"config_id", "plan_hash": "sha256:…", "would_create": 3, "skipped_identical": 1, "metrics": [{"metric_id","metric_name","object_name","client_name","action": "create|skip_identical"}]}}`. `metric_ids` limits the candidates to a subset of the matches (an id that does not match -> 422).
- `preview: false` requires `confirm: true` (else 409 `confirmation_required`) and the `plan_hash` from the preview (409 `preview_stale` if the matches or existing rules changed). One transaction creates one rule per `create` metric; "identical" means same type, operator, threshold, reference period, consecutive updates, severity, cooldown on the same metric; identical rules are skipped, never duplicated. One audit event per created rule (`source UI`, category `bams`). Response `{"ok": true, "item": {"created": 3, "skipped_identical": 1, "rule_ids": […]}, "side_effects": []}`. No silent bulk write is possible: nothing is applied without a preview hash.

### 11.9 Notifications

`GET /api/bams/notifications?limit=50&unread_only=false` -> `{"ok": true, "unread_count": 3, "items": [{"id": 412, "event_id": "…", "kind": "opened|recovered|closed", "attempted_at": "…Z", "title": "Warning opened: CPU utilisation %", "detail": "Castellan Peak / BPOD-NY-01 · value 91.4", "severity": "Warning", "unread": true, "status": "open"}]}`. Items are the `in_app` channel rows of `bams_notification_log`, newest first (limit 1..200). In-app text carries names and values; **Privacy Mode affects desktop toasts only** ("BAMS alert opened (Critical)", no account, appliance or value). `kind "reminder"` is not produced in this run.

`POST /api/bams/notifications/read`: `{"through_id": 412}` or `{"all": true}` (exactly one; unknown id/extra -> 422). Marks everything up to that log id read (a watermark kept in `app_meta` `bams.notifications_read_through`; no schema change) and returns `{"ok": true, "item": {"unread_count": 0}}`. Notification rows are never deleted by this route. Recording is once per event/kind/channel (DB unique); a desktop failure is logged at warning and never fails a poll or a request.

### 11.10 DEV-only routes (`/api/dev/bams/*`)

Registered only when the runtime is DEV; in PROD every one answers 404 `not_found` as if absent, and they cannot change mode, provider kind or `simulated`. Bodies strict. All return `{"ok": true, "item": {…}, "side_effects": []}`.

| route | body | effect |
|---|---|---|
| `POST /force-value` | `{"metric_id", "value": number, "poll": true}` | the simulator reports `value` (fresh timestamp) from the next poll on; `poll: true` (default) also runs one poll cycle now and returns `{"monitor", "row"}` |
| `POST /simulate-stale` | `{"metric_id"\|null, "on": true}` | the metric (or all) stops receiving source updates (age grows with the clock) |
| `POST /simulate-outage` | `{"on": true}` | provider unavailable (banner, No Data, lifecycle frozen) |
| `POST /poll` **(+)** | `{}` | run exactly one poll cycle now (works while the monitor is stopped) |
| `POST /clock` **(+)** | `{"advance_seconds": 90}` or `{"set": "…Z"}` or `{"reset": true}` | moves the injectable clock (D-61) used by the monitor, lifecycle and freshness; `server_time` follows it |
| `POST /reset` | `{"confirm": true}` | `pre-delete` backup, then clears alert events, notification log, samples and overrides, re-backfills 90 days of simulated history; keeps appliances, metrics, rules, templates and settings |

Without `confirm` `reset` answers 409 `confirmation_required`. A PROD runtime also refuses to start with any of these enabled (§1).

### 11.11 Behaviour notes

1. **Reads never poll.** Only the monitor loop (or `/api/dev/bams/poll`) calls the provider; provider calls per minute depend only on `poll_interval_seconds`.
2. **Counts agree everywhere.** `summary.active_alerts`, the account Infrastructure `active_alerts`, `/api/state` `infrastructure` and the Today `bams_alert` rows all use "events with status open or recovered on enabled items".
3. **Audit and activity.** Every write route here produces `audit_events` (category `bams`, `source UI`; import: §12). Alert opened/recovered/closed system entries and the `b:<event id>:<what>` keys are unchanged (§3, §7); opened/recovered are written by the monitor with `source Monitor`.
4. **Frozen evaluation** (stale or outage) leaves events, counters and suppression untouched; only a human Close works.
5. **Logging.** The monitor logs poll cycles at debug and failures at warning with no values, tickers lists or secrets; browser disconnects are debug (§0).
6. **Rate/size.** No route returns more than the caps above; bodies are 2 MiB (§0.1a).

### 11.12 Deviations, schema findings and decisions for PM/DA/FE

0. **Implementation notes (2026-10-14, T-102..T-109; reality differs from the text above in these places).** (a) `POST /api/bams/rule/delete` is **blocked** while the rule has a non-closed alert: 409 `conflict`, `details.reason "active_alert"` (the schema trigger `trg_bams_alert_rules_no_delete_active` forbids it); close the alert first. (h) Default DEV monitor starts with the server; tests run without the loop thread.

4. **No schema change required** (agrees with DA T-101/T-122): `bams_alert_rules.suppress_until_clear` is the runtime suppression flag, set by Close-while-breaching and cleared on recovery; the notification read state is a watermark in `app_meta` `bams.notifications_read_through` (DA: no read flag column; the bell number in mockup 07 is "unread", so this watermark is required and is not a schema change).
5. **Additive routes beyond PM §12.3 (+)**: `GET /api/bams/monitor`, object/metric `delete-preview`, `configs/save|delete`, dev `poll` and `clock`.

### 14.3 Restore from file
**Upload cap 25 MiB per file** (413 `payload_too_large` `details.reason "too_large"`); max 10,000 rows per sheet / file and 50,000 in total (422 `invalid_file` `reason "too_many_rows"`). A session lives 10 minutes after its last use (in memory, max 3 unapplied sessions; the oldest is dropped), results are kept 1 hour. Unknown/expired id -> 410 `import_expired`.

**`POST /api/restore/inspect`** raw body, headers `X-File-Name`; query `session` (add the file to that session; CSV only) and `table` (one of the keys of 14.0, forces the table of a CSV). **Writes nothing.** One `.xlsx` (the whole workbook; the About sheet is required) **or** one to nine `.csv` files (one per table, added one call each), never mixed. Response `item` = the **Plan** below (also returned by GET, remove, table).
Refusals are 422 `invalid_file` with `details.reason`: `not_an_export` (no About sheet, wrong app, no schema/channel), `schema_newer` ("made by a newer version"), `schema_older`, `channel_mismatch` (a DEV export into PROD: "Sample data cannot be restored into the production database"; PROD into DEV is allowed), `header_missing` (xlsx sheet lacks required columns; `details.missing`, `details.sheet`), `header_duplicate`, `mixed_formats`, `xlsx_single` (second workbook), `table_already_added` ("Accounts is already added; remove it first."), `too_many_files`, `too_many_rows`, plus the Run 3/4 reasons (`unsupported_type`, `not_xlsx`, `not_csv`, `corrupt`, `encrypted`, `macros`, `external_links`, `embedded_objects`, `xml_unsafe`, `zip_unsafe`). Unrecognized CSV headers are **not** an error: the file is staged with `table: null`.
CSV rules: decoding (BOM, UTF-8, UTF-16, Windows-1252), delimiter sniffing (comma, semicolon, tab, pipe), plain-text cells, row 1 = headers. **Table detection (D-135):** the tables whose required columns are all present are candidates; the one matching most of its columns wins; a tie is Unrecognized (the file name only breaks a tie). `table_source`: `sheets` (xlsx), `headers`, `filename`, `chosen`, `none`.

Applied sessions -> 409 `already_applied` with `details.result`. `GET /api/restore/inspect` and `/apply` -> 405.

**`POST /api/restore/apply`** `{restore_id, plan_hash, confirm: true}`. Existing rows are never touched. **Audit:** one event per staged table: `category data`, `object_type import`, `object_id` = database table name (`clients`, ...), `action restored`, `source Bulk Import`, `new {added, identical, skipped_differs, skipped_invalid}`.

### 14.5 Restore database (implemented, T-184/T-185)
Replaces the whole live database. `.db` upload cap **500 MiB** (`too_large`), free disk >= 3x file size (`no_space`). One staged session at a time, 10-minute TTL. Staged file in `<data>/restore_tmp/`, never in Backups.
- `POST /api/restore/database/inspect` raw `.db` body (`X-File-Name`) -> Preview. `POST /api/restore/database/from-backup {name}` (name must be a current Backups-list entry; no paths) -> Preview. `GET /api/restore/database/{id}` -> Preview. `POST /api/restore/database/{id}/cancel` -> `{ok, item: {cancelled: true}}`.
- **Preview** `item`: `{restore_id, expires_at, source: {kind: "upload|backup", name}, file: {schema_version, will_upgrade_from: n|null, latest_activity: "…Z"|null, channel, counts: {accounts, contacts, tasks, notes, appliances, metrics, quarters, upgrade_records, audit_events, bams_history}}, current: {same shape}, fewer: ["notes", …] (tables where file < current), warning: "Everything currently in the app will be replaced. A safety backup is taken first and stays in the Backups list.", confirm_word: "RESTORE"}`.
- Refusal codes on inspect (422 unless noted): `not_sqlite` (first 16 bytes), `too_large` (413), `no_space` (507-style plain 422), `integrity_failed` (integrity_check or foreign_key_check), `schema_newer`, `channel_mismatch` (DEV db into PROD and PROD db into DEV), `no_channel_stamp`, `migration_failed` (older schema migrated on the staged copy only), plus `restore_expired` (410) for unknown/expired ids.
- `POST /api/restore/database/apply {restore_id, confirm: "RESTORE"}`: wrong word -> 409 `confirm_mismatch`. Takes a `pre-restore` backup (never auto-pruned), raises the maintenance gate (other requests get `503 restoring`, `Retry-After: 2`, except `GET /api/state/health`), stops the monitor, swaps atomically (`.restore-new` / `.pre-restore-old`), verifies, writes an audit event (`category data`, `object_type` backup|schema, `action restored`, `source System`), restarts the monitor as before, clears sessions/caches. Success `item`: `{restored: true, backup: {name,…}, counts: {…}, schema_version}`; the UI reloads. Failure 500 `restore_failed` with `details.state` = `"unchanged"` ("Your data was not changed") or `"safety_backup"` (`details.backup`: "Restored from safety backup <name>"). A second apply with the same id -> 410 `restore_expired`.

**As built (14.5 clarifications, 2026-10-15).**
- Upload cap 500 MiB (`/api/restore/database/inspect` is exempt from the 2 MiB default; body streamed to `<data>/restore_tmp/`). `no_space` and `integrity_failed` etc. are 422, `too_large` is 413. `from-backup` with a name not in the Backups list -> 404 `not_found`. Startup, exit, cancel, expiry and a newer inspect all delete staged files.
- Health during a swap is `GET /api/health` (not `/api/state/health`): it answers `{"ok": true, "restoring": true, ...}` without opening the database and is never gated. Every other `/api/*` request during the swap gets `503 restoring` with `Retry-After: 2`; non-API paths (the static UI) are not gated.
- `confirm` must equal `RESTORE` exactly (no trimming, case-sensitive) -> else 409 `confirm_mismatch`, checked before anything else; the staged session stays valid.
- Refusal checks, in order: SQLite header (`not_sqlite`); read-only open, `integrity_check` and `foreign_key_check` (`integrity_failed`); our `application_id` and an `app_meta` table (`not_sqlite`); channel stamp (`no_channel_stamp`, `channel_mismatch`, also a mock-seeded file in PROD); newer schema (`schema_newer`); then the migration runner always runs on the staged copy (upgrades an older file; for an equal version it still verifies the guard triggers, so a file with undeclared triggers is refused as `integrity_failed`; an upgrade that fails -> `migration_failed`).
- Preview `item.file` / `item.current`: `{schema_version, will_upgrade_from, latest_activity, channel, counts}` with counts for `accounts, contacts, tasks, notes, appliances, metrics, quarters, upgrade_records, audit_events, bams_history`; `fewer` lists keys where the file has fewer rows than the current database.
- Apply failure `restore_failed` (500) `details`: `state` = `unchanged` | `safety_backup` | `needs_attention` (rollback itself failed; message tells the user to keep the safety backup), `backup` (the `pre-restore` file name), `swapped` (bool). The staged session is kept after a failure so the user can retry; the gate is always reopened and the monitor restored to its prior state. If requests do not drain within 10 s or a BAMS poll is still running, apply returns `restore_failed` / `unchanged` without having touched anything.
- Success `item`: `{restored: true, backup: {name, reason "pre-restore", size_bytes, created_at}, counts, schema_version, source}`; the post-swap audit event is `category data`, `object_type backup`, `object_id` = safety backup name, `action restored`, `source System`.
- Startup recovery runs before the database is opened: a leftover `.restore-new` is deleted; a leftover `.pre-restore-old` is put back if the live file is missing or fails integrity, otherwise deleted; `restore_tmp/` is cleared.

**Upload cap behaviour (413 delivery fix, 2026-10-15).** When a request is over its cap the server now reads and discards the rest of the body (bounded: 1 GiB, 60 s, 1 s idle; never stored, so the cap is unchanged) BEFORE it sends `413 payload_too_large`, then closes the connection. Applies to every route (2 MiB default; 5 MiB import inspect; 25 MiB `/api/restore/inspect`; 500 MiB `/api/restore/database/inspect`). The response shape is unchanged.

## 16. Database name (TAM_DB_NAME, 2026-10-16)
- **Env var `TAM_DB_NAME`** (optional, PROD and DEV): a bare name; the server appends `.db`. Rules: 1-40 characters from `A-Z a-z 0-9 _ -` only (no dots, spaces, slashes, `..`, non-ASCII), not a reserved Windows device name (`CON PRN AUX NUL COM1-9 LPT1-9`, any case); the resolved file must sit directly inside the data folder. Blank or unset = the default (`tam_command_center` in PROD, `tam_dev` in DEV; `tam_command_center` is refused in DEV). A bad value stops the start with a plain message (exit code 3); nothing is created.
- A new name creates a brand-new empty database (migrations run, no seed in PROD; DEV seeds sample data unless `TAM_DEV_SEED=0`). An existing file with that name is simply opened; no file is ever overwritten, renamed or deleted by choosing a name. Each database is stamped with its channel as before.
- **Per-database files:** instance lock `<name>.db.lock` (two databases can run at the same time only on different ports via `TAM_PORT`; the second start on a busy port stops before touching any file with exit code 5 and the message "Port N is already in use ... set TAM_PORT"; the same database twice is still refused by its lock, exit code 2). The default database keeps `TAM_Backups/`, `logs/`, `restore_tmp/` exactly as before (existing backups stay visible); a named database uses `TAM_Backups/<name>/`, `logs/<name>/`, `restore_tmp_<name>/`. Backups list, safety backups, database copy and database restore (section 14.5) always act on the active database only.
- **Shown:** startup log line `database: <path> (name: <name>, selected by TAM_DB_NAME|default)`; `GET /api/state` `runtime.db_name` and `GET /api/health` `db_name` (next to the existing `db_path`).

## 17. BAMS freshness semantics (2026-10-16)
- `last_received` = time of the last successful valid observation of the metric (updated on EVERY successful poll, even when the value is unchanged). `last_source_update` = time the VALUE last changed; it advances only on a real change. `age_seconds` and `freshness` (Live/Delayed/Stale) are derived from `last_received`; `No Data` when there is no value or no `last_received`, and always when the provider is unavailable. The dashboard sort key `last_update` follows `last_received`.
- Monitor: each successful observation updates `last_received`, runs alert evaluation (so consecutive-observation rules count unchanged values) and refreshes monitor health. A change-history sample (`bams_metric_samples`) and `current_value`/`last_source_update` are written only when the value changed. A failed poll or a poll that returns nothing for a metric never advances `last_received`, so a real outage still ages Live -> Delayed -> Stale. A clock that did not advance (frozen DEV mock clock) skips ingestion as before (QA-E5-3).
- Metrics that never had a value stay `No Data` and open no stale alert on any poll path.

- **Kinds:** every item of `GET /api/data/backups` gains `kind`: `"weekly"` (reason `weekly`, automatic), `"safety"` (reasons `pre-import`, `pre-delete`, `pre-migration`, `pre-restore`, any other `pre-*`: taken before a risky change) or `"manual"` (reason `manual`, "Create backup now" = `POST /api/data/backup`, unchanged). The list is **newest first** (by creation stamp) so the UI can group by `kind`; `reason` is still returned. Each database lists only its own folder (section 16).
- **Weekly:** on app start and then every hour while running, if the database holds data (at least one account, task, note or appliance) and no `weekly` backup exists from the last 7 days, one `weekly` backup is taken with the online backup API. Never more than one per 7 days; a failure is logged and retried at the next check.
- **Retention (automatic, runs after every backup and after the weekly check):** keep the newest **8** `weekly`; of each safety reason keep the newest **5**, and delete any safety backup older than **30 days**; **`pre-restore` and `manual` backups are never deleted automatically**; the single newest backup of any kind is never deleted. Age/ordering come from the stamp in the file name.

### 18.4 Application log: download and weekly cleanup (2026-10-16)
Scope: the **application log files only** (`tam_command_center.log` and its rotated copies `tam_command_center.log.1` ... in the log folder of the ACTIVE database: `logs/` for the default database, `logs/<name>/` for a named one, section 16). **The audit log (`audit_events`) is a different thing: it is never touched by this feature; it has its own 14-day retention (18.5) and its own CSV/Excel export (18.2).** Backups, database files and `restore_tmp` are never touched or included.
- **`GET /api/logs/download`** (the "Download logs" button). Query `file`: `zip` (default) or `current`. There is no path or name parameter; the server only ever reads the regular files named `tam_command_center.log` / `tam_command_center.log.<n>` directly inside the active log folder (sub-folders, symlinks to other places and every other file are ignored).
  - `zip`: one `application/zip` containing the current log plus every rotated file, `Content-Disposition: attachment; filename="tam_logs_<YYYYMMDD>.zip"`. Entry names are the bare file names.
  - `current`: the current log as `text/plain; charset=utf-8`, `filename="tam_command_center_<YYYYMMDD>.log"`.
  - `Cache-Control: no-store`. Size cap: 50 MiB of log data; over that the oldest rotated files are left out of the zip (the current file is always included; the response header `X-Log-Files-Omitted: <n>` says how many). No log folder or no file yet -> 200 with an empty zip / empty text. Writes no audit event. Invalid `file` -> 422.
  - Secrets: the server never logs tokens, cookies, request headers or bodies, metric values or tickers lists (checked 2026-10-16). Log lines do contain the database path, account-independent counts and the **file names** of imports/exports/restores and the Bloomberg host/port, so treat the downloaded logs as local, internal files.
- **Weekly cleanup** (same scheduler as the weekly backup: runs at app start and on the hourly check, but acts at most once per 7 days, remembered in the file `log_cleanup.stamp` inside the log folder, which is never included in downloads): (1) if the current log file is larger than 5 MiB it is rotated first; (2) rotated files older than **7 days** (file modification time) are deleted; (3) if the log folder's log files still exceed **50 MiB** the oldest rotated files are deleted first until under the cap; the current log file is never deleted. One info line records what was cleaned (`log cleanup: removed N files (X KiB), kept M`). Failures are logged and never stop the app.

### 18.5 Audit log retention: entries older than 14 days are removed every 14 days (schema 2, 2026-10-16)
- **Rule (user decision, overrides "append-only" for OLD rows only):** every 14 days the server deletes `audit_events` rows older than 14 days. There is no "Prune now" route and no delete route. UI text: "Entries older than 14 days are removed every 2 weeks. Last cleaned: <last_pruned_at>" (never -> "not yet").
- **Schema 2 (migration `0002_audit_prune.sql`, `db/schema.sql` kept in sync):** the guard `trg_audit_events_no_delete` now aborts a DELETE only when the row is newer than 14 days (SQLite clock, UTC); UPDATE stays refused; re-using an id stays refused (ids are AUTOINCREMENT, so pruned ids are never reissued). So even a bug cannot remove recent history. An existing database is upgraded at start: the runner first takes a `pre-migration` safety backup, runs the migration in one transaction and rolls back on any error (the app then refuses to start with the database still at version 1).
- **Job:** runs from the hourly scheduler. The first start only records the cycle start (`app_meta` `audit.prune.anchor`); the first prune is 14 days later; each run (`audit.prune.last_run`, also the new anchor) is persisted, so restarts neither skip nor double a run. No safety backup is taken. One info log line `audit prune: removed N entries older than 14 days` per run, and, when N > 0, ONE audit event: `category system`, `object_type schema`, `object_id audit_events`, `action pruned`, `source System`, `reason "pruned N entries older than 14 days"`.
- **Meta for the UI:** `GET /api/audit` and `GET /api/audit/facets` return `retention: {retention_days: 14, interval_days: 14, last_pruned_at: "…Z"|null, next_due_at: "…Z"|null}`.
- **What loses data after a prune:** the Audit log page and its CSV/Excel export (nothing older than 14 days), and Today "Recently changed" (the newest 20 rows are read with no date window, so on a quiet database it can show fewer than 20 items). Unaffected: the done-today ring (today only), Activity and the activity-trend sparkline (notes only), per-account views (notes/tasks tables), DB-restore previews ("latest activity" = newest row). The 14-day window is also the only history the app keeps of who changed what.

**Migration failure handling (QA-8-1).** Any failure while applying a migration (bad SQL, disk full) is rolled back as a whole and reported as a refused database, never a crash: the server prints `TAM Command Center cannot start: Database refused: <file> failed and was rolled back (...)` and exits with code 4; the `pre-migration` safety backup stays in the Backups folder and the database stays at its old version. The same failure while a database restore is being staged (an older file that cannot be upgraded) returns 422 `migration_failed` ("This backup cannot be upgraded; nothing was changed."), never a 500.
