## 0. Conventions

- Base: `http://127.0.0.1:<port>` (PROD 8765, DEV 8766, `TAM_PORT` overrides). Loopback only. Requests whose `Host` is not `127.0.0.1` or `localhost` are refused (DNS-rebinding guard). Non-GET requests with an `Origin` header must be same-origin, or (DEV only) the Vite origin `http://127.0.0.1:5173` / `http://localhost:5173`; otherwise 403 `forbidden_origin`. CORS is enabled only for those DEV origins.
- All bodies are JSON (`Content-Type: application/json`). All responses are JSON and carry `Cache-Control: no-store`.
- **Unknown request fields are rejected** (422). Strings are trimmed; an empty string on an optional field means `null`.
- **Dates** are `YYYY-MM-DD` (no timezone, local calendar date, D-06). **Instants** are UTC `YYYY-MM-DDTHH:MM:SS.sssZ`. Input instants may carry an offset or omit milliseconds; they are normalised to UTC. An input with no offset is treated as UTC.
- **Booleans** are JSON booleans (`is_primary`, `archived`, `enabled`).
- Every row payload includes `row_version` (integer). Send it back as `expected_row_version` on updates (D-11).
- "Today" (`today`) is the workstation's local date, computed by the server.

### 0.1 Envelopes

Success: `{"ok": true, ...}`. Mutations return `{"ok": true, "item": {...}, "side_effects": [...]}` (`side_effects` is always present, possibly `[]`).

Side effects are objects with a `type`:

| type | extra fields | meaning |
|---|---|---|
| `primary_cleared` | `contact_id`, `name` | contact `contact_id` was primary and has been cleared by this save (toast: "B is now primary (was A)") |
| `next_contact_updated` | `client_id`, `old`, `new` | D-07: the account's `next_contact` was moved |
| `last_contact_updated` | `client_id`, `old`, `new` | D-08: the account's `last_contact` was moved |
| `backup_created` | `file`, `reason` | a safety backup was written before a delete |
| `no_change` | | the save changed nothing; `row_version` was not bumped and nothing was audited |

Error:
```json
{"ok": false, "error": {"code": "validation_error", "message": "Request validation failed.",
                        "fields": {"due": "must be a date in YYYY-MM-DD format"},
                        "details": {}}}
```
`fields` appears on `validation_error` and field-level `conflict`; `details` is an optional free-form object (additive).

| code | HTTP | when |
|---|---|---|
| `validation_error` | 422 | schema/enum/date/length/unknown-field errors, unknown referenced account |
| `not_found` | 404 | unknown id or unknown `/api/...` path |
| `confirmation_required` | 409 | `*/delete` without `confirm: true` (or account delete without matching `confirm_name`) |
| `stale_write` | 409 | `expected_row_version` does not match. `details.current_row_version` is given |
| `conflict` | 409 | uniqueness: duplicate account name (case-insensitive), second primary contact, ... |
| `payload_too_large` | 413 | request body over 2 MB (`details.max_bytes`); checked before the body is parsed (additive, Phase 4.1) |
| `not_implemented` | 501 | later-phase route |
| `method_not_allowed` | 405 | wrong method on a known path, with an `Allow` header and `details.allowed` (additive; before Phase 4.1 `/api/...` paths answered 404) |
| `forbidden_origin` | 403 | cross-origin write / bad Host (additive) |
| `backup_failed` | 500 | the safety backup could not be written; the delete did **not** happen |
| `internal` | 500 | unexpected error (details are in the server log, not in the response) |

### 0.1a Response headers and limits (Phase 4.1, additive)
Every response, including errors and the SPA, carries `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`. The compiled bundle loads with no violations. Request bodies larger than 2 MiB (`MAX_BODY_BYTES`, declared or chunked) get 413 `payload_too_large`. The largest legitimate body (a 50000-character note) is far below the cap.

### 0.2 Update semantics

`POST /api/<object>/save` is an upsert: **no `id` creates, `id` updates**. Updates are **patches**: only the fields present in the body change; send `null` to clear an optional field. Required fields on create are listed per route. `id` is generated by the server (UUID4) and cannot be supplied on create.

If `expected_row_version` is sent and differs from the stored `row_version` -> 409 `stale_write`. If it is omitted, the write is unconditional. Updating a missing id -> 404 `not_found`.

## 4. Writes

All writes are one SQLite transaction containing the data change **and** its `audit_events` row(s). All return `{"ok": true, "item": ..., "side_effects": [...]}` with the saved row. HTTP 200 for create and update.

### `POST /api/client/save`
| field | type | notes |
|---|---|---|
| `id` | string | omit to create |
| `expected_row_version` | int | update only |
| `name` | string 1..200 | required on create; unique case-insensitive -> 409 `conflict`; no tab/CR/LF |
| `bpid` | string ≤32 \| null | |
| `products` | string ≤500 \| null | |
| `status` | `Active` \| `Inactive` | default `Active` |
| `next_contact` | date \| null | |
| `notes` | string ≤20000 \| null | |

Returns an **Account** (with `counts`). Audit: `client.created`; on update one `client.next_contact_changed` and/or `client.status_changed` row for those fields, plus one `client.updated` row for the remaining changed fields.

### `POST /api/client/delete`
`{"id", "confirm": true, "confirm_name": "<exact account name>", "expected_row_version"?}`. Missing `confirm` or a `confirm_name` that does not equal the stored name (exact, trimmed) -> 409 `confirmation_required`. A `pre-delete` safety backup is taken first; if that fails -> 500 `backup_failed` and nothing is deleted. Cascades to contacts, notes, tasks, upgrades and BAMS objects (D-12). Audit `client.deleted` (history survives). Returns `{"ok": true, "item": {"id": "…", "name": "…"}, "side_effects": [{"type": "backup_created", ...}]}`.

### `POST /api/contact/save`
Fields: `id`, `expected_row_version`, `client_id` (required on create; immutable afterwards), `name` (1..200), `role` (≤200), `email` (≤254, optional, must look like `x@y.z`), `team` (≤200), `is_primary` (bool, default false).

Primary rule: setting `is_primary: true` clears any other primary of the same account **in the same transaction**; side effect `primary_cleared`. An account may have zero primaries. Audit: `contact.created` / `contact.updated` for field changes, plus `contact.primary_changed` (`old_value.primary_contact`, `new_value.primary_contact`) when the primary designation changes. "Make primary" is `{"id", "is_primary": true}`.

### `POST /api/contact/delete`
`{"id", "confirm": true, "expected_row_version"?}`; safety backup first; audit `contact.deleted`.

### `POST /api/task/save`
Fields: `id`, `expected_row_version`, `task` (1..500, no tab/CR/LF, required on create), `client_id` (nullable), `category` (default `Other`), `priority` (default `Medium`), `status` (default `Not Started`), `due`, `next_update`, `waiting` (≤500), `notes` (≤20000), `update_next_contact` (bool, default **false**; see D-07).

- D-07: when `update_next_contact` is true, `category` is `Client Follow-Up`, `client_id` and `due` are set, and the account's `next_contact` is empty or later than `due`, the account's `next_contact` is set to `due` in the same transaction (own audit row, `source=System`); side effect `next_contact_updated`. Quick Capture "Client Follow-Up" sends `true` by default (the checkbox).
- Audit: `task.created`; `task.completed` when status becomes `Complete`; `task.reopened` when it leaves `Complete`; otherwise `task.updated`.
- Mark complete: `{"id", "expected_row_version", "status": "Complete"}`.

### `POST /api/task/archive`
`{"id", "archived": true|false, "expected_row_version"?}` -> audit `task.archived` / `task.unarchived`.

### `POST /api/task/delete`
`{"id", "confirm": true, "expected_row_version"?}`; safety backup first; audit `task.deleted`.

### `POST /api/note/save`
Fields: `id`, `expected_row_version`, `client_id` (required on create; immutable), `note_type` (required on create), `timestamp` (instant; default now), `subject` (≤200), `body` (≤50000), `action_items` (≤10000). At least one of `subject`/`body` must be non-empty. `source` is not accepted (server sets `GUI`).
D-08: saving a `Meeting Note` or `Call Note` whose local date is later than `last_contact` sets `last_contact` (audit `client.last_contact_changed`, `source=System`); side effect `last_contact_updated`. General Notes never do.
Audit: `note.created` / `note.updated`.

### `POST /api/note/delete`
`{"id", "confirm": true, "expected_row_version"?}`; safety backup first; audit `note.deleted` (shows in Activity as "Meeting Note deleted: <subject>").

### Backups
- `POST /api/data/backup` (body `{}`) -> `{"ok": true, "item": {"name","reason":"manual","size_bytes","created_at"}, "side_effects": []}`. Online-backup-API copy; verified with `integrity_check`. Audit `backup.created`.
- `GET /api/data/backups?limit=20` -> `{"ok": true, "items": [{"name","reason","schema_version","size_bytes","created_at"}], "backup_dir": "…"}` newest first. Retention: automatic backups (`pre-delete`, `pre-migration`) keep the 30 most recent; manual are never pruned (D-22).

### `POST /api/dev/reseed` (DEV only)
`{"confirm": true}` -> safety backup (`pre-delete`), then resets the DEV DB to the mock seed (settings kept). Returns `{"ok": true, "item": {"counts": {...}}, "side_effects": [backup_created]}`. **Not registered in PROD** (404 `not_found`).

## 9. Run 2 additions (additive; T-62 to T-64, PM-AC-1..3, D-27 D-29 D-31 D-33)

No frozen field, route or error code changes. No schema change. All three are read-only GETs, loopback-only, `Cache-Control: no-store`, with the usual security headers.

### 9.1 `progress` on `GET /api/today` (PM-AC-1, D-29)
```json
"progress": {"day": "2026-10-13", "total": 8, "done": 3, "open": 5, "done_other": 1}
```
All five keys are always present; the four counts are integers >= 0. `day` echoes `today`. `total = done + open`, so `done <= total` always. `queue`, `upcoming`, `recent_changes` and `account_load` are unchanged (same items, same order).

Rules (PM §10.2, executed by the reference query `db/queries/day_progress.sql` unmodified): tasks only. Plan task = `due IS NOT NULL AND due <= today`, account Active or none, and either open (status not Complete, not archived) or done today. `done` = plan tasks with status Complete now and a `task`/`completed` audit row inside the local-day window (counted once per task; archived is ignored for done tasks). `open` = open plan tasks. `done_other` = completed today under the same rules but `due > today` or `due` NULL. Tasks on Inactive accounts are excluded from all four. Deleted tasks are not counted.

Day window: the server converts the local midnight of `today` and the local midnight of `today + 1 day` to UTC **separately** (`[start, end)`), so a 23-hour or 25-hour DST day is exact. The timezone is the workstation zone (the same clock as `today`).

### 9.2 `GET /api/accounts/activity-trend?days=14` (PM-AC-2, D-31)
Query: `days` (optional, default and only accepted value **14**; any other value -> 422 `validation_error`; the query is fixed at 14 buckets), `include_inactive` (optional boolean `true|false`, default `false`).
```json
{"ok": true, "today": "2026-10-13", "days": 14,
 "series": {"<client_id>": [0, 2, 0, 1, 0, 0, 3, 0, 0, 1, 4, 0, 2, 5], "<client_id>": [0, 0, ... 14 ints]}}
```
`series` has one key per Active account (all accounts with `include_inactive=true`), each an array of exactly `days` non-negative integers, **oldest first**: index 0 is `today - 13`, index 13 is `today`. A point is the number of Activity-timeline entries (the union in `activity_timeline.sql`: manual notes, listed system events, BAMS alert opened/recovered/closed, no filter) on that local day. Accounts with no activity return 14 zeros. Deleted notes and objects behave as in the Activity timeline. Executed via `db/queries/activity_trend.sql` unmodified; each of the 15 bucket edges is a separately converted local midnight (DST-exact). Series keys are not ordered; use the account list for order.

### 9.3 `server_tiles` on `GET /api/client/{id}/infrastructure` (PM-AC-3, D-31)
**Naming note:** PM-AC-3 proposed the key `servers`, but `servers` is already a frozen integer (the distinct server count) on this payload, so the array is published as **`server_tiles`**. `servers` (integer) is unchanged. `/api/state` `infrastructure` does **not** carry `server_tiles` (it stays light, §42); only this per-account endpoint does.
```json
"server_tiles": [
  {"name": "bxa-ny-01", "environment": "PROD", "version": "7.1.4", "alert_severity": "Critical",
   "spark": {"metric": "Disk", "window_hours": 168, "points": [["2026-10-06T12:00:00.000Z", 71.2], ["2026-10-06T18:00:00.000Z", 73.0]]}},
  {"name": "bxa-ldn-02", "environment": "DEV", "version": null, "alert_severity": null, "spark": null}
]
```
One tile per **distinct server name** (case-insensitive across `bams_objects.name` and `server_upgrades.server_name`), ordered by name (case-insensitive, then exact). The first-seen spelling is used (BAMS object name preferred).

| field | rule |
|---|---|
| `name` | server name |
| `environment` | `PROD` / `DEV` / `null`; same precedence as the `environment_summary` (upgrade rows, most recent release first, else the BAMS object) |
| `version` | `current_version` of the server's earliest open upgrade (status not Completed/Deferred, by `scheduled_date`, nulls last), else `target_version` of its latest Completed upgrade, else `null` |
| `alert_severity` | `Critical` / `Warning` / `Info` = worst **open** alert on the server's enabled BAMS metrics, else `null` (healthy) |
| `spark` | object or `null` |

`spark` metric choice (one metric per server): (1) the metric of the server's highest-severity open alert (ties: earliest `opened_at`, then id); else (2) an enabled metric whose name contains `cpu` (case-insensitive; ties by name, then id); else none. `spark` is `null` when there is no such metric, the server exists only as upgrade records, or the chosen metric has no samples in the window. Never invented.

Window: samples with `sampled_at` in the last 7 days (queried by `metric_id` and a `sampled_at` range only; older rows are never read, §45). `window_hours` = whole hours from the first sample in the window to now, rounded up, capped at 168 (so "CPU 24h" for a day of data, "Disk 7d" at 168). `points` = `[iso_utc, value]` pairs, oldest first, **at most 28**: if the window holds more than 28 samples, the span from the first to the last sample is split into 28 equal-time buckets and each non-empty bucket contributes its maximum value at that sample's timestamp. PROD has no `spark` until the Phase 4 monitor writes samples.

### 10.1 `GET /api/import/accounts/template?format=xlsx|csv` (default `xlsx`)

### 10.2 `POST /api/import/accounts/inspect`
Request: the raw file bytes as the body (no multipart). Headers: `Content-Type: application/octet-stream` (not trusted), `X-File-Name: <percent-encoded name>` (display only, <= 200 chars, path parts stripped; **its extension must be `.xlsx` or `.csv`**, and the content must match, see `invalid_file`). The browser type is never trusted. Body cap **5 MiB for this route only**. **Writes nothing** (no audit, no backup, no database write).

Response `200`:
```json
{"ok": true, "item": {
  "import_id": "b6f1…32 hex", "plan_hash": "sha256:…", "expires_at": "2026-10-13T15:12:00.000Z",
  "file": {"name": "accounts_q4_import.xlsx", "size_bytes": 18432, "format": "xlsx", "sheet": "Accounts",
           "rows_found": 40, "encoding": null, "delimiter": null, "notes": []},
  "limits": {"max_rows": 500, "max_candidates": 5, "max_bytes": 5242880},
  "counts": {"rows": 40, "valid": 37, "new": 24, "updates": 6, "needs_review": 7, "invalid": 3, "unchanged": 1},
  "warnings": [{"code": "unknown_column", "text": "Column G \"Region\" is ignored."}],
  "rows": [ <Row>, … ]
}, "side_effects": []}
```
- `file.format` is `"xlsx"` or `"csv"` (decided from content AND extension). For csv: `sheet` is `"CSV"`, `encoding` is `"UTF-8"`, `"UTF-8 (with BOM)"`, `"UTF-16"` or `"Windows-1252"`, `delimiter` is `"comma"`, `"semicolon"`, `"tab"` or `"pipe"`, and `notes` holds one display sentence, e.g. `"Read as CSV: encoding UTF-8, delimiter semicolon."`. For xlsx these three are `null` / `null` / `[]`. In CSV every cell is plain text: a cell that starts with `=` is data, not a formula; a leading `'` before `=`, `+`, `-`, `@` (written by our own CSV export) is removed.
- `counts`: `valid = new + updates + needs_review`; `rows = valid + invalid`; `unchanged` is the subset of `updates` with nothing to fill.
- `rows` is ordered by Excel row number (CSV: record number; row 1 is the header). **Row**:
```json
{"row": 4, "state": "new|update|needs_review|invalid",
 "values": {"name": "Web Ltd", "bpid": "104233", "products": "B-PIPE", "status": "Active", "next_contact": "2026-11-05", "notes": null},
 "raw": null,
 "errors": [{"field": "status", "code": "status_not_allowed", "text": "Row 7: Status: 'Dormant' is not in the list (Active, Inactive). This row will be skipped; fix it in the file and re-upload, or leave it out."}],
 "warnings": [{"code": "different_bpid", "text": "BPID in the file (1) differs from the account's BPID (2); the existing BPID is kept."}],
 "match": null, "candidates": [], "merged_into": {"row": 3}, "unchanged": false}
```
  `values` are normalised (status canonical case, date `YYYY-MM-DD`, empty -> `null`, whitespace collapsed, control characters removed). For `invalid` rows `values` holds the fields that parsed and `raw` holds the cell texts (strings, each <= 500 chars here); otherwise `raw` is `null`. `merged_into` is present only on an in-file exact duplicate (same `exact_key` as an earlier valid row): its `state` is `update` when the earlier row is an update, else `new`; it follows the earlier row's resolution (including Skip) and never needs its own decision. `unchanged` is present on `update` rows. Row error codes: `name_required`, `name_too_long`, `bpid_too_long`, `bpid_invalid`, `products_too_long`, `notes_too_long`, `status_not_allowed`, `date_invalid`, `formula_not_allowed`, `cell_error`, `value_type`. Warning codes: row `different_bpid`, `bpid_used_elsewhere`; file `unknown_column`.

- `needs_review` rows carry `candidates` (<= 5, ordered High, Medium, Low, then more reasons first, then name casefold, then id):
```json
{"ref": {"type": "account", "id": "…"},
 "name": "Web Mgmt Ltd", "bpid": "104233", "products": "Terminal", "status": "Active", "next_contact": null, "row_version": 4,
 "strength": "High",
 "reasons": [{"code": "contained_name", "text": "Every word of Web also appears in Web Mgmt Ltd"}, {"code": "same_bpid", "text": "Same BPID: 104233"}],
 "differences": [{"code": "different_bpid", "text": "Different BPID: file 1, existing 2"}],
 "fills": {"products": "B-PIPE", "next_contact": "2026-11-05"},
 "kept": {"products": {"existing": "Terminal", "file": "B-PIPE", "differs": true}},
 "notes": []}
```
  `ref` is `{"type":"account","id":…}` or `{"type":"row","row":13}` (an earlier valid, non-merged row; then `row_version` is absent). `fills`/`kept` assume "Same account" with that candidate. `strength` is `"High" | "Medium" | "Low"`. Reason and difference codes: `same_core_name`, `same_words_spelled_differently`, `abbreviation`, `contained_name`, `shared_key_words`, `similar_spelling`, `same_bpid`, `exact_name`, `different_bpid`; the texts are fixed backend sentences (display them; do not rebuild them).
- A row is exactly one of the four states. Sessions: at most 3 unapplied in memory; inspecting a 4th discards the oldest. Only parsed rows are kept, never the file.

### 10.4 `POST /api/import/accounts/apply`
```json
{"import_id": "b6f1…", "plan_hash": "sha256:…", "confirm": true,
 "decisions": [
   {"row": 4,  "choice": "same",      "target": {"type": "account", "id": "…"}},
   {"row": 6,  "choice": "different"},
   {"row": 14, "choice": "same",      "target": {"type": "row", "row": 13}},
   {"row": 33, "choice": "skip"}
 ]}
```
Unknown fields are rejected (422). Order of checks: `confirm` must be `true` (else 409 `confirmation_required`); session (410 `import_expired`; 409 `already_applied`); another Apply running (409 `conflict`); the plan is **re-run against the current database** and its `plan_hash` compared (409 `preview_stale`); `decisions` validated against the fresh plan (422 `validation_error` for a duplicate entry, a row that is not `needs_review`, `same` without `target`, a `target` on `different`/`skip`, a `target` that is not one of that row's candidates, or `same` onto a row that is skipped); a `needs_review` row without a decision -> 409 `unresolved_duplicates` (`details.rows`). Then, only if the plan changes something: the `pre-import` backup (online backup API; `backup_failed` 500, nothing written); `BEGIN IMMEDIATE`; `row_version` of every touched account re-checked and the whole plan re-hashed **inside the transaction** (409 `preview_stale`, rollback); all creates and fills; **one `audit_events` row per created or updated account**; `COMMIT`. Any exception rolls the whole transaction back. If the plan changes nothing: no backup, no transaction, no audit, `backup: null`.

Merge rules (D-43): fill blanks only (`bpid`, `products`, `next_contact`, `notes`); a non-blank value is never changed, appended to or replaced; an Inactive account stays Inactive; earlier rows win over later rows; a new account's blank Status becomes `Active`.

### 10.10 Security and operations notes
CSP, Origin and Host rules apply unchanged (the upload is a same-origin `fetch`). The body is capped by the ASGI body-limit middleware before the route reads it. The reader never extracts to disk and never opens a file by an archive-supplied path. Only parsed rows are kept in memory (not the file) and nothing from the file is logged: logs record file name, format, sizes, counts and outcomes. Only one Apply runs at a time (process lock). `GET /openapi.json` (DEV) lists the routes.
